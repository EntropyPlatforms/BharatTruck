# `supabase/schema/` — what the database IS

`baseline.sql` is a DDL snapshot of schema `public`, generated by introspecting the live
`bharattruck-mvp` catalog. It is the **authoritative description of the current schema**.
If you want to know what a column is called, whether a foreign key cascades, which tables
have RLS, or who can execute a function — read `baseline.sql`. It was produced from the
database, so it cannot drift from the database except by the database changing after it
was generated.

`supabase/migrations/*.sql` is **history: how we got here**. It is not a description of
the current state and must never be read as one. It is missing `0001`–`0008` entirely —
the DDL that created `users`, `bookings`, `drivers`, `vehicles`, `quotes` and most of the
founding tables was never committed to this repo — so anyone reconstructing the schema by
reading migrations builds a confident but badly incomplete picture. See
`supabase/migrations/README.md` for the full account and for which files are applied.

## The rules

**Do not hand-edit `baseline.sql`.** It describes what exists. An edit changes nothing in
the database; it only makes the file wrong until someone regenerates it and silently
reverts your change. To change the schema: write a new numbered migration, apply it, then
regenerate the baseline in the same PR.

**Migrations are applied BY HAND. CD never applies them.** The deploy pipeline builds and
ships services; it does not touch the database. Someone with access runs the SQL against
the project — historically through the Supabase MCP `execute_sql`, since `apply_migration`
is blocked by this harness's classifier. That is why applied-state has to be established
by looking at the catalog rather than by trusting an automated record: nothing automated
ever wrote one.

**Apply the migration to prod BEFORE you merge the PR — never after.** CD ships the code the
moment the PR merges (usually within ~2 minutes), so if the table or column the new code reads
is not there yet, every request 503s until someone remembers to run the SQL — this is precisely
the `fleet_members` outage. Additive DDL is forward-safe: a new table/column sits unused until
the code that reads it deploys, so applying it early never breaks the currently-running (old)
revision. "Apply first, then merge" is therefore always safe, and it is the order to follow.
CI enforces it — a PR that touches `supabase/migrations/` fails the **migration hand-apply gate**
(`.github/workflows/ci.yml`) until it carries the `migrations-applied` label, which whoever ran
the SQL adds as an attestation (the check re-runs on the label). Two one-time setup steps make
the gate real: create the `migrations-applied` label (Issues → Labels), and mark "migration
hand-apply gate" a **required status check** on `main` (Settings → Branches) — without that a red
check is only advisory and can still be merged past.

**Determine "is migration N applied?" by checking whether its objects exist.** Not by
reading `supabase_migrations.schema_migrations`. That ledger is populated by hand, its
`version` values are Supabase-CLI timestamps that do not correspond to our `NNNN_` file
numbers, some rows are named after a file and some are not, and at least one applied
migration has no row at all. It is evidence, not an answer.

## Regenerating

`scripts/db/dump-schema.md` has every query, in order, with the exact exclusion rules
(extension-owned objects out, constraint-backing indexes out) and the verification step.
Follow it top to bottom and replace `baseline.sql` wholesale — do not patch it by hand
against a diff.

Regenerate whenever you apply a migration. A stale baseline is worse than none, because
people trust this file by design.

## What the baseline covers

Extensions, enum types (labels in sort order — that order is semantic), tables with exact
types/nullability/defaults/generated expressions, all constraints via
`pg_get_constraintdef`, indexes via `pg_indexes.indexdef`, functions via
`pg_get_functiondef`, triggers via `pg_get_triggerdef`, views via `pg_get_viewdef`, RLS
enablement and every policy, all table/column/function comments, and grants.

It deliberately does **not** cover: the `auth`, `storage`, `graphql`, `vault` and
`extensions` schemas (Supabase-owned), objects owned by extensions inside `public`
(PostGIS's `spatial_ref_sys`, `geometry_columns`, `geography_columns` and 744 functions),
roles, or data. `CREATE EXTENSION` recreates the extension-owned objects.
